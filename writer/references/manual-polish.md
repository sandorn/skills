# 纯手动逐章逐段润色模式

完全规避子代理并发卡死问题，100% 可控的润色模式，所有改动都是主 AI 模型在当前会话上下文里亲手完成的。

---

## 核心原则

### 三零原则

1. **零修改脚本**：不调用任何会修改文件的脚本。只读脚本允许（`audit.py --verify` 验证）。
2. **零子代理**：完全不使用子代理委派（sub-agent delegation），不 spawn 任何子 Agent
3. **零批量替换**：不使用 sed/awk/正则批量替换，每处改动逐句阅读后手动判断

### 子代理边界（防破窗指引）

「零子代理」不是口号，是每一章都要守住的底线。以下场景是常见破窗点——AI 容易自我合理化"这不算是子代理"：

| 诱惑场景 | ❌ 破窗做法 | ✅ 正确做法 |
|---------|-----------|-----------|
| 检查章节字数是否 ≥2500 | 调 `pad_chapter.py --check` 或 spawn 子代理统计 | 主模型肉眼估算：行数 × 每行平均字数；不确定时多算一遍 |
| 扫描 AI 高频词 | 调 `audit.py` 或 `grep` 批量扫 | 逐句阅读时眼睛自带扫描——读完一章你自然知道哪些句子不对劲 |
| 检查段落超长 | 调 `split_paragraphs.py --dry-run` | 逐段目测：超过 3 行的段落基本超标，手动拆分 |
| 批量统计优化点 | spawn 子代理逐章统计 | 润一章记一章，进度文件手动累加，不靠事后回忆 |
| 章末钩子力度评分 | 调 `analyze_hook.py` | 对照技法手册 4.3 节四条标准，人工判断 |
| 对话引号批量检查 | `grep '"'` 扫 ASCII 引号 | 润色时逐句改写对话，引号自然同时修正 |
| 「似乎/仿佛」密度统计 | `grep -c` 计数 | 读的时候感觉到"这个词出现太多了"——直接删，不需要精确计数 |
| 章节润后字数不足，需要补 | 调 `pad_chapter.py` | 主模型写补充内容：找该章最薄弱的场景，展开 1-2 段画面描写 |

**底线规则**：
- 不通过子代理执行任何 Python 脚本
- 不通过子代理读取/分析文件内容（即使 agent_type 为只读）
- 所有质量判断由主模型在上下文中完成
- **宁可漏判一处，不可开子代理的口子**——漏判只影响一章，破窗影响全书

### 润色哲学

- **微调而非重写**：每章改动控制在 5-15%，避免"越改越不像原文"
- **增强而非替换**：在原文基础上提升画面感和爽点节奏，不替换作者的表达习惯
- **保真优先**：宁可少改一处，不可改错一处。不确定的改动 → 保留原文
- **润色 ≠ 只修禁令**：画面感、节奏、对话、信息密度四个维度必须全部覆盖。不能把「纯手动润色」降级为「禁令扫描 + 污染修复」——那样等于没做润色。

## 常见陷阱与教训

### 陷阱一：「不→是」污染（批量修复脚本后遗症）

**症状**：大批章节中「不」被替换为「是」，如「不疼」→「是疼」、「不知道」→「是知道」、「不了」→「是了」。

**成因**：使用正则或 `replace('不是', '')` 式的批量修复脚本时，替换逻辑不精确，误伤了正常文本。

**检测方法**：逐章通读时，用眼睛扫描以下高频误伤模式：
- `是疼` `是胀` `是错` `是到` `是敢` `是急` `是能` `是像`
- `是起` `是懂` `是够` `是怕` `是对劲` `是知道` `是同意`
- `是正常` `是清楚` `是会` `是服` `是响` `是酸` `是爽`

**修复原则**：逐处判断上下文，只修明确误伤的，不再次批量替换。

### 陷阱二：把禁令审查当润色

**症状**：通读后只修了破折号、AI高频词、B03违禁句式，没有对画面感、节奏、对话做任何创作性增强。

**判断标准**：如果一章润完后，没有新增任何感官细节、没有调整任何句长节奏、没有优化任何对话标签——那就是没润，只是审。

**正确做法**：禁令修复是润色的**前置步骤**，不是润色本身。每章至少标记并执行 3-5 处创作性微调。

### 陷阱三：用自动扫描替代逐章报告

**症状**：写一个 Python 脚本扫描所有章节，批量输出结果，一次性报告几十章。

**用户反感信号**：「你为啥要加速」「不能逐章报告吗」「不用脚本」。

**正确做法**：每章独立通读→独立标记→独立修复→独立报告。一章一帖，不给用户「你在偷懒」的感觉。

### 陷阱四：把「润色」降级为「禁令修复 + 污染清除」

**症状**：通读后只修了破折号、AI高频词、B03违禁句式、「不→是」污染残留，没有对画面感、节奏、对话做任何创作性增强。报告只有「N处污染+N处润色」但没有改前→改后例句。

**用户反感信号**：「这些不符合手动润色的要求」「你是不是只做了禁令审查」

**判断标准**：如果一章润完后，维度报告中没有画面/节奏/对话/密度任一列的具体数字和改前→改后例句——那就是没润，只是审。

**正确做法**：禁令修复和污染清除是润色的**前置步骤**，不是润色本身。每章至少标记并执行 3 处创作性微调，并在报告中给出具体例句。

## 硬性规则（必须严格遵守）

### 润色操作规范

1. **全量逐章阅读**：每章完整读完至少一遍，理解上下文后再动笔
2. **逐句微观调整**：只优化措辞、语气、语态，不动核心情节
3. **画面感+爽点节奏**：优化目标是提升画面感和爽点节奏
4. **核心情节 100% 不动**：所有原始情节、人物对话、结构框架完整保留
5. **一章一结**：每章润完立即写回，不攒到内存批量写
6. **优化点实时记录**：每章改完后立即记录优化点，不靠事后回忆

### 交付规范

1. **统一交付**：全部润完后统一汇总给用户确认
2. **中途不打断**：润色过程中不打扰用户，不输出中间状态（除非遇到阻塞问题）
3. **交付报告**：润完后提供完整的交付报告（含逐章明细）

### writer 硬性禁令（润色中同步遵守）

1. **破折号清零**：正文中不得出现 `——`
2. **「不是…而是…」句式禁用**
3. **元叙事标签禁用**
4. **对话必须用 `「」`**：不得出现 `"..."` 或 `'...'`
5. **AI 高频词禁用**：他知道/忽然/突然/眼中闪过一丝/深吸一口气/心中一动/似乎/仿佛
6. **段落按句号断段**：单段 ≤42 汉字
7. **每章 ≥2500 汉字**

## 执行流程

### Step 0：启动前检查

1. 确认项目根目录（检测 `writer.json` + `setting/` + `chapters/`）
2. 读取 `writer.json` 获取当前写作状态
3. 检查 `.writer/runtime/` 是否存在上次未完成的润色进度文件

```
检查清单：
□ 项目根已确认
□ 当前写作状态已读取（卷数/已完成章数/当前章）
□ 正文路径已确认（chapters/ 或 chapters/）
□ 上次润色进度已检查（如有中断则提示续润）
```

### Step 1：确认润色范围

向用户确认（以下信息不全时追问，否则直接执行）：

1. **润色范围**：起止章节（如 ch03-ch60）
2. **润色目标**（可多选）：
   - 画面感提升（默认开启）
   - 爽点节奏优化（默认开启）
   - 对话自然度
   - 信息密度调整（删冗余+补断层）
   - 全维度润色（以上全部）
3. **力度偏好**：
   - 轻（每章改动 ≤5%，几乎看不出改了）
   - 中（每章改动 5-10%，有明显提升但保持原味）
   - 重（每章改动 10-15%，显著提升但不越界）

### Step 2：创建进度追踪文件

润色开始前，在 `tracking/manual-polish-progress.md`（或 `追踪/润色进度.md`）写入：

```markdown
# 纯手动润色进度

## 项目信息
- 书名：{writer.json 中的 project}
- 总章数：{chapters_total}
- 开始时间：{timestamp}
- 润色力度：轻/中/重
- 润色目标：画面感/爽点/对话/信息密度/全维度

## 进度总览
- 已完成：0 / {总章数}
- 进行中：-
- 剩余：{总章数}

## 逐章记录

| 序号 | 章节 | 状态 | 词汇优化 | 句式调整 | 画面增强 | 节奏优化 | 备注 |
|------|------|------|---------|---------|---------|---------|------|
| 1 | ch_003 | ⏳ | - | - | - | - | - |
```

### Step 3：逐章润色循环

对每一章执行以下 8 步：

```
对于每一章：
  ① 从文件系统读取正文（`cat chapters/ch_{NNN}.md`）
  → ② 完整通读一遍
  → ③ 标记微调点 → ④ 执行逐句调整
  → ⑤ 自检清单 → ⑥ 写回文件 + 立即 mirror 到数据库
  → ⑦ 记录优化点 → ⑧ 更新进度文件
```

#### ③ 标记微调点

通读时在心里标注：

- `[画面]` 此处可加入感官细节
- `[节奏]` 此段句长单一/爽点被压缩
- `[对话]` 标签生硬/不够口语化
- `[冗余]` 可删的 AI 高频词/重复修饰
- `[断层]` 此处缺空间/时间/身份锚点
- `[钩子]` 章末钩子力度不足
- `[污染]` 疑似「不→是」误伤残留

#### 逐章闸门（进入下一章前必须自答，任一为「否」禁止前进）

```
□ 我是否完整通读了本章每一行？（不是跳读、不是扫关键词、不是依赖脚本输出）
□ 我是否在本章中标记并执行了 ≥3 处创作性微调？（画面/节奏/对话/密度四维度，不含禁令修复和污染清除）
□ 我对本章的润色报告是否包含：维度数量表 + 至少一条改前→改后例句 + 禁令自查结论？
```

#### ⑦ 记录格式（在对话中逐章报告，禁止退化）

每章润完后立即在对话中报告。**每章报告至少包含**：
- 一个带具体数字的维度表格（画面N/节奏N/对话N/密度N/污染N）
- 至少一条「改前→改后」的具体例句
- 禁令自查结论

**禁止以下退化形式**：
```
❌ "chXX: ✅ 无污染 1润色"
❌ "chXX-YY 全清，批量完成"
❌ "全清。关键章加画面润色，其余快速过。"
❌ 用脚本扫描结果替代逐章通读报告
```

维度表格格式：

```
## chNN 润色报告

| 维度 | 处数 | 改前→改后示例 |
|------|------|-------------|
| 画面感 | N | 「原句」→「新句」 |
| 节奏 | N | ... |
| 对话 | N | ... |
| 密度 | N | ... |
| 污染修复 | N | ... |
| 禁令 | ✅ | 破折号0/AI词0/B030 |
```
然后更新 `tracking/manual-polish-progress.md` 中的进度行。

润色后逐章自检清单：

```
□ AI 高频词已清除（他知道/忽然/突然/似乎/仿佛/眼中闪过一丝/深吸一口气/心中一动）
□ 对话全用「」，无 ASCII 引号残留
□ 无「——」破折号
□ 无「不是…而是…」句式
□ 无元叙事标签
□ 每段 ≤42 汉字
□ 全章 ≥2500 中文汉字
□ 核心情节/对话内容/伏笔未动
```

每章润完后记录优化点类型和数量，在进度文件逐章行追加。

润色完成后更新版本状态：
```bash
# 更新 writer.json 版本记录（final）
# 章节文件即真实来源
```

### Step 4：自动审查 + 交付

润色完成后自动激发审查（润色可能引入新问题）：

```bash
# 最低审查：daily 8维
python scripts/audit.py chapters/       # 禁令扫描
# 若润色 ≥5章，升级为 solo 15维深度审查
```

审查通过后生成交付报告（见下方模板）。

## 逐章质检清单（完整版）

润完每一章后，逐项确认：

### 禁令层（Blocking — 必须清零）

```
□ [P0] AI 高频词清零：「他知道」「忽然」「突然」「似乎」「仿佛」
              「眼中闪过一丝」「深吸一口气」「心中一动」
□ [P0] 破折号清零：「——」
□ [P0] 对话引号全用「」
□ [P0] 「不是…而是…」清零
□ [P0] 元叙事标签清零
```

### 段落层

```
□ [P1] 无超标段落（每段 ≤42 汉字，含标点）
□ [P1] 段落数 ≥ 总字数 / 55（段落密度达标）
□ [P2] 对话独立成段
```

### 字数层

```
□ [P1] 中文汉字 ≥2500（不含标点空格换行）
□ [P2] 若非尾章，不超 4500 中文汉字
```

### 内容保真层

```
□ [P0] 核心情节走向未动
□ [P0] 人物对话内容未改
□ [P0] 伏笔位置/内容未动
□ [P0] 等级/金币/战力/时间数值未变
□ [P2] 角色说话风格保持一致
```

### 润色效果层（自评）

```
□ [P2] 画面感：每 500 字至少 1 处感官细节（视觉之外）
□ [P2] 爽点节奏：关键爽点场景是否用了三拍子
□ [P2] 钩子强度：章末 500 字是否有明确的悬念/反转/威胁/期待
□ [P3] 对话自然度：对话标签是否过度依赖"说/道"
```

```markdown
- ✅ 人物对话内容完整保留
- ✅ 伏笔位置/内容未动
- ✅ 等级/金币/数值未变
- ✅ 润后所有章节已逐章自检通过
```

## 异常处理

### 中断恢复

润色过程中若会话中断，恢复流程：

1. 读取 `tracking/manual-polish-progress.md`
2. 找到最后一个状态为 `✅` 的章节
3. 从下一章 `⏳` 或 `🔄` 继续
4. 如果某章状态 `🔄`（润色中但未完成）：
   - 读取该章当前内容，从 `git diff`（如有）或文件修改时间推断已完成部分
   - 若无法确定进度，该章重新润一遍（开销小，不会重复犯错）

```
中断恢复检查清单：
□ 进度文件存在 → 读取续润
□ 进度文件不存在 → 扫描 chapters/ 最后修改时间，推断进度
□ 无法推断 → 从范围起始章重新润（三零原则保证无副作用）
```

### 误改回滚

- 每次润色前，建议先 `git add` / `git commit`（如项目有 git）
- 若无 git，润前先留一份原始备份：`cp chapters/ch_xxx.md chapters/ch_xxx.md.bak`
- 发现某章改坏 → 从备份恢复，重润该章

### 用户中途叫停

- 收到用户叫停指令时，立即完成当前章的自检+写回+进度更新
- 不保存中间状态的润色结果
- 告知用户已完成到第几章

### 润色效果不佳

- 如果某章润后字数变化 >20%，说明改动过重，应检查是否越界到"重写"
- 如果某章润后字数 <2500，必须标记为阻塞，不可交付
- 如果连续 3 章优化点 <5 处，说明润色力度偏轻，和用户确认是否提高力度

## 与其他润色模式的关系

| 模式 | 子代理 | 脚本 | 批量替换 | 可控性 | 适用场景 |
|------|--------|------|----------|--------|---------|
| **纯手动逐章逐段** | ❌ | ❌ | ❌ | 100% | 作者对质量极度敏感/需要逐句掌控 |
| 全量优化（optimize.md） | ✅ | ✅ | ✅ | 中 | 批量提升效率优先，接受自动化 |
| 去AI味（quality.md deslop） | ❌ | ✅ | ✅ | 高 | 针对性清除 AI 痕迹 |
| 审查修订（review → revise） | ✅ | ✅ | ✅ | 中高 | 审查驱动的定向修复 |

选择指引：
- **精准度 > 速度** → 纯手动润色（本文件）
- **效率 > 完美** → 全量优化（`optimize.md`）
- **只需去 AI 味** → quality.md deslop（`quality.md`，适用 ≥10 章批量快速清除）
- **审查发现问题后的修复** → review + revise 管线
