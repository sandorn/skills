# 卷审查协议（Volume Audit Protocol）

> 用于已完成的整卷质量审计（非破坏性，不修改文件）。
> 适用于写作过程中任何阶段的回溯检查。

---

## 审计范围确认

**输入**：用户指定"审查第X卷"或"全面审查"
**自动化判断**：
1. 读取 `novel-pipeline.json` 获取 `volume` 定义、章节范围、标题
2. 若未有卷定义，通过章节文件编号推断（ch01~ch30 → 第1卷）
3. 确认细纲文件存在（`outline/outline-volumeN.md`）

---

## Step 1: 加载参照基准

| 数据源 | 用途 |
|--------|------|
| `state-files/world_setting.json` | 世界观层级、地理、势力、特殊规则 |
| `state-files/characters.json` | 角色人设（personality_traits/speech_style/core_values/bottom_lines） |
| `state-files/power_system.json` | 境界体系、装备等级、战力规则、系统机制 |
| `state-files/foreshadowing.json` | 活跃伏笔列表（status/expected_payoff_window/hints_placed） |
| `outline/outline-volumeN.md` | 卷细纲（每章关键剧情点） |

---

## Step 2: 批量读章

- 按章节编号顺序读取全部 `ch{N:03d}.md` 文件（如 `ch001.md`、`ch010.md`）
- 每章标注：章号、标题（# 开头第一行）、字符数、行数
- 记录异常：空章节、格式错误、标题缺失

### 性能优化：子代理并行读章

当审查整卷（≥50章）时，逐章串行读取会耗尽上下文窗口。应采用 **子代理并行读取** 模式：

```python
# 在 Agent 会话中调用 delegate_task
delegate_task(
    goal="读取并审查第N-M章的全部正文，对比细纲...",
    context="(传递项目路径、已有审查发现、细纲文件路径)",
    toolsets=["terminal", "file"]
)
```

**最佳实践**：
对于中等规模的卷（30-50章），**推荐采用"直接读+子代理"混合模式**：

1. **前10章直接读取**：主 Agent 直接用 `read_file` 阅读开头章节，掌握文风、叙事节奏、关键设定
2. **剩余章节派子代理**：将剩余章节拆成 2-3 批，每批 10-15 章，派子代理并行读取
3. **要点统一**：在 `context` 中传递已发现的关键设定偏移和审查要求，确保子代理使用统一标准
4. **结论本 Agent 汇总**：子代理报告返回后，主 Agent 整合前后段结论，输出统一报告

**优势**：既避免了全量串行读取的上下文窗口爆炸，又保证了关键章节的审查深度。
- 子代理返回的是**自述报告**，不是已验证的事实。关键判定（OOC/设定冲突）需主 Agent 在汇总时二次验证

## Step 3: Round 1 — OOC 一致性检查

### 逐人物检查清单
| 人物字段 | 检查方法 | 判定标准 |
|---------|---------|---------|
| `personality_traits` | 逐章找出该角色的行为/对话，看是否与性格特征冲突 | 胆小者不该主动冲锋；好面子的人受辱应有合理反应 |
| `speech_style` | 检查角色的对话风格是否一致 | 话少型突然长篇大论即 OOC；阴阳怪气的人突然诚恳需有理由 |
| `core_values` | 检查关键决策是否触碰核心价值观 | 正义角色不该无故滥杀；重情义的人不该背叛 |
| `bottom_lines` | 检查是否突破底线 | 如有突破，需细纲标注弧线 + ≥3章铺垫 |
| `cultivation_level` | 检查战力表现是否在合理范围内 | 跨级战斗需有系统/装备/禁术等合理解释 |

### 弧线判定
- 性格渐变需要细纲标注弧线方向
- 突变（无铺垫）→ OOC阻断
- 合理渐变（有铺垫）→ 标注为"弧线进展"

### 特殊案例
- 反派的行为转换：林浩然在秘境中救主角 → 需提供合理解释（"被石子绊了一下"等）
- 卧底的伪装与暴露：暴露前与暴露后的行为应形成鲜明对比

---

## Step 4: Round 2 — 剧情/伏笔执行检查

### 细纲覆盖度检查
1. 将细纲每章的剧情点拆解为关键点列表
2. 逐章在正文中检查每个关键点是否被执行
3. 统计覆盖率 = (已执行点数 / 总点数) × 100%

| 覆盖率 | 判定 |
|--------|------|
| ≥ 90% | ✅ 优秀 |
| 80-89% | ⚠️ 良好，记录未覆盖项 |
| 60-79% | ⚡ 缺失较多，建议补充 |
| < 60% | ❌ 阻断，需重写 |

### 伏笔推进状态检查
1. 读取 `foreshadowing.json` 中 `status="unresolved"` 的伏笔
2. 检查 `expected_payoff_window` 是否覆盖本卷范围
3. 逐条判断本卷内伏笔的推进状态：

| 状态 | 定义 |
|------|------|
| ✅ 推进 | 本章新增了线索、暗示或部分揭示 |
| ✅ 回收 | 本章完全解答或引爆了该伏笔 |
| ⏳ 未触及 | 窗口期覆盖本卷但正文未涉及 |
| ❌ 矛盾 | 正文信息与伏笔设定冲突 |

---

## Step 5: Round 3 — 逻辑/战力/设定冲突检查

### 跨章一致性检查
| 检查维度 | 方法 |
|---------|------|
| 修为爬升曲线 | 绘制主角/重要角色每章的修为变化 → 检查是否有跳跃式突破 |
| 装备等级变化 | 记录装备获取/更换的时间点和品阶 → 检查是否超出修为限制 |
| 地理移动 | 记录每章角色位置 → 检查移动时间是否合理 |
| 时间线 | 用相对时间词（三天后/七日后/半个月）构建时间轴 → 检查是否有矛盾 |
| 势力关系 | 检查势力间的关系是否贯穿一致（同盟/敌对/中立） |

### 逐章内部一致性检查
- 数值前后矛盾（如第6章说练气四层，第10章又写"练气一层对练气六层"）
- 设定自相矛盾（如前文说某地无人，后文又出现有人活动）
- 系统提示/界面数据与正文状态不一致

### 常见问题模式
```
1. 敛息术导致的明面修为 vs 真实修为混淆
   → 需在系统数据框中明确区分「明面修为」和「真实战力」
2. 气运值/积分数值的突变缺乏中间过渡
   → 建议补充每日衰减说明或剧情事件触发的扣减
3. 不同卷/章作者换模型导致的设定偏移
   → 需在卷边界处做对照检查
```

## 性能优化：子代理并行读章

当审查整卷（≥50章）时，逐章串行读取会耗尽上下文窗口。应采用 **子代理并行读取** 模式：

```python
delegate_task(
    goal="读取并审查第N-M章的全部正文，对比细纲...",
    context="(传递项目路径、已有审查发现、细纲文件路径)",
    toolsets=["terminal", "file"]
)
```

**最佳实践**：
- 10章以内：直接 read_file 串行读取（可控）
- 10-30章：拆为2-3个子代理并行
- 30-50章：拆为3-5个子代理，每批10-15章

### ⚠️ 批量修正的两大陷阱

**陷阱1：单脚本多文件修改中途 assert 中断**

```python
# ❌ 错误模式：所有修改在内存中累积，一个 assert 失败就全丢
fix_file('ch006.md')
fix_file('ch10.md')  # 此处 assert 失败 → 脚本 exit(1)
fix_file('ch16.md')  # 永远不会执行，ch06 的修改也未写入
```

✅ **正确做法**：每修改一个文件就立即保存，或拆成独立脚本逐个运行。写 `tmp_fix.py` 时，让每个 `fix_file()` 调用内部自己完成"读→改→写"：

**陷阱2：多段插入脚本在中间 assert 失败时丢失已成功段的插入**

当需要在同一个文件中插入多个段落时（如ch81需同时插入ch37旁白+碎月印记+血渊亮相+追兵身份），不要把所有修改都写在一个脚本中最后一次性写入。如果中间的assert失败，前面的修改也会丢失。

✅ 更可靠的模式：每段修复后立即保存，或拆成独立脚本逐个运行。

### ⚠️ 子代理报告二次验证（重要）

| 误报类型 | 实际案例 | 处理方式 |
|---------|---------|---------|
| 声称某文件中有某内容但实际不存在 | 子代理报告"ch46日记说林青云已死"，实际原文为"天煞以为我死了" | 关键证据必须 `read_file` 原文确认 |
| 夸大问题严重度 | 报告"修为体系严重混乱5处矛盾"，实际部分为敛息术导致的合理降级 | 逐条定位原文再判断 |
| 遗漏已解决的问题 | 子代理可能不会读取最新版文件 | 执行任何修改前确认文件版本 |

**工作流**：子代理报告 → 主 Agent 抽样读原文验证 ≥3 处 → 确认属实后执行修正 → 修正后二次验证

## 审查后修正工作流

当审计报告识别出问题后：

1. **非批量修正**（1-3个孤立问题）：直接用 `patch` 工具定位修复
2. **批量修正**（10+个散布在多个文件中的同类问题）：用 Python 脚本做 str.replace：
   - write_file 写 .tmp_fix.py（含 assert 验证）
   - terminal 执行脚本
   - Remove-Item 清理
   - 二次验证：Python 检查所有标记是否命中
4. **伏笔/人物更新**：构建 JSON payload → `python hooks/archive_state.py` 写入 state-files
5. **跨卷伏笔延续检查**：见下方独立章节
6. **修为级联问题**：如果中间某章将主角修为提前突破，后续所有提到修为的段落在批量修正时需统一处理——不能只改一处。修复流程：确定基准修为→搜索全卷"练气X层"→批量替换为"筑基X层"→处理冗余突破剧情→归档到state-files。改后必须二次验证所有标记章节。

## 跨卷伏笔延续管理

卷审查时，重点检查 `foreshadowing.json` 中 `expected_payoff_window` 覆盖本卷但**全程未触及**的伏笔。

### 伏笔跨卷延续检查流程

1. 加载 `foreshadowing.json`，筛选 `status="unresolved"` 且 `expected_payoff_window` 起止范围与本卷有交集的伏笔
2. 逐条检查正文中是否出现了与伏笔相关的关键词/暗示/事件
3. 判定结果：

| 状态 | 含义 | 处理 |
|------|------|------|
| ✅ 推进 | 本章新增线索或暗示 | 无需额外操作 |
| ✅ 回收 | 完全解答或引爆 | 标记为 resolved |
| ⏳ 窗口未到 | payoff_window 尚未进入本卷 | 无需处理 |
| ⚠️ 跳过 | 窗口期在本卷但正文未涉及 | 调整 payoff_window 顺延至下一卷 |
| ❌ 遗忘 | 窗口期在本卷且完全未提及 | 在下卷开头安排回收 |

## 新增检查：卷间连续性检测

卷边界是最容易出现连续性断裂的地方。每次跨卷审查时，必须对**前 5 章做三向交叉校验**（state-files × 前卷结尾 × 本卷开头）：

### 三向校验检查表

| 检查项 | 数据源 A | 数据源 B | 发现断裂的检测方法 |
|--------|---------|---------|------------------|
| ① 人物修为 | characters.json | 本卷正文开头 | Python 扫开头 500 字的修为关键词 vs state-files |
| ② 地理位置 | world_setting.json + 前卷末章 | 本卷开头场景 | 检查前卷结尾的传送/移动 vs 本卷开场位置 |
| ③ 已获物品 | power_system.json | 本卷角色使用物品 | 检查前卷获得的特殊道具是否被遗忘 |
| ④ 角色生死 | characters.json(status) | 本卷正文提及 | 已故角色不应在对话中自然出现 |
| ⑤ 伏笔窗口 | foreshadowing.json | 本卷内容 | 窗口期在本卷但未触及的伏笔列表 |

### 本会话实际发现的 S1 级卷间断裂（应每天审查时主动检测）

| 断裂类型 | 章节 | 现象 | 根因 | 修复方案 |
|---------|------|------|------|---------|
| **场景跳变** | vol2 ch80→vol3 ch81 | ch80结尾众人传送至丹塔修炼室，ch81开头回到天魔岭战场密林 | 无过渡/闪回标记+两句说明 | 加前导句：「从丹塔传送阵出来已是三日后。众人返回天魔岭崩塌处取回遗留物资。」 |
| **修为回退** | ch91 | 写"早已卡在练气八层巅峰"，但 vol2 ch48 已筑基初期 | 跨模型写作时前卷剧情未传递 | 替换「练气八层」为「筑基初期」 |
| **世界层错乱** | ch110 | 写"整个九天灵域的天空被撕开"，但故事仍在苍玄大陆青云宗 | 素材库/草稿混入灵界设定 | 替换为「青云宗上空的天空」 |
| **伏笔断线** | ch28→ch81→至今 | ch28埋血渊/碎月，ch81提"找上门来了"，但ch82-180从未出现 | 新设定/剧情线挤出了旧伏笔 | 尽快安排回收，或明确标记为延后伏笔 |

### 如何自动检测这些断裂

```python
# 跨卷连续性检测脚本模板
import json, os, re

def check_volume_transition(volume_start_ch, prev_volume_end_ch):
    """检测 volume_start_ch 和 prev_volume_end_ch 之间的连续性"""
    
    # 1. 检查 characters.json 中的修为 vs 正文
    chars = json.load(open('state-files/characters.json', encoding='utf-8'))
    for ch_num in [volume_start_ch, volume_start_ch+1, volume_start_ch+2]:
        text = open(f'chapters/ch{ch_num}.md', encoding='utf-8').read()
        for c in chars['characters']:
            name = c['name']
            expected_level = c.get('cultivation_level', '')
            if expected_level and name in text:
                # 检查正文中是否出现与 expected_level 矛盾的旧修为
                # (具体实现取决于修为命名规则)
                pass
    
    # 2. 检查前卷结尾与本卷开头的位置连续性
    # 提取前卷末尾200字中的地点关键词
    end_text = open(f'chapters/ch{prev_volume_end_ch}.md', encoding='utf-8').read()[-200:]
    start_text = open(f'chapters/ch{volume_start_ch}.md', encoding='utf-8').read()[:200]
    # 对比看是否在同一地点
    print(f'前卷末场景: {end_text[:100]}')
    print(f'本卷首场景: {start_text[:100]}')
    
    # 3. 检查 foreshadowing.json 中窗口到期的伏笔
    foreshadow = json.load(open('state-files/foreshadowing.json', encoding='utf-8'))
    for f in foreshadow.get('active', []):
        window = f.get('expected_payoff_window', '')
        # 检查窗口是否覆盖本卷起止
        if window and volume_start_ch < 200:  # 简化检查
            print(f'[F] {f["id"]} {f["description"][:40]}... 窗口={window}')
```

## 新增检查：被遗忘的伏笔检测

长篇写作中，早期埋下的伏笔容易被新加入的剧情线挤出焦点。这种遗忘在跨卷审查中尤其致命——因为每一卷都在产生大量新设定、新冲突，旧伏笔会自然沉底。

### 追踪方法

1. 加载 `foreshadowing.json`，筛选 `status="unresolved"`
2. 对每条伏笔，用关键词在目标卷全章中搜索
3. 检查伏笔的 `expected_payoff_window` 是否与本卷有交集

### 本会话实际案例

| 伏笔 | 首次埋入 | 后续提及 | 当前状态 | 风险等级 |
|------|---------|---------|---------|---------|
| f-005 碎月印记 | ch27 (卷1) | ch81「碎月印记。血渊。他们终于主动找上门来了。」 | **连续4卷未真正推进** | 🔴 故事线断裂 |
| f-006 血渊组织 | ch28 (卷1) | ch81 同一处 | **同上** | 🔴 |
| f-010 段长老 | ch68 (卷2) | 从未再次出现 | 连续2卷消失 | 🟡 |

### 修复策略（策略 A/B 决策树）

| 场景 | 推荐策略 | 做法 |
|------|---------|------|
| 伏笔在后续卷**从未被提及** | 策略A：延后 payoff_window | 在 foreshadowing.json 中把窗口顺延到最近一卷，并添加备注 |
| 伏笔在后续卷**被提及但未推进**（如 ch81 血渊） | 策略B：安排实际剧情回收 | 让伏笔背后势力在该卷真正出手，避免「雷声大雨点小」 |
| 伏笔对当前主线**已无影响** | 策略A：放弃 | 在 foreshadowing.json 标记为 `deprecated`，不回收也不强求 |

### 预防措施

为每条伏笔增加 `last_hinted_chapter` 字段，每次审查时自动计算「从最近一次提示至今的章数间隔」。超过 50 章未提示的伏笔标记为 ⚠️ 遗忘风险：

  "id": "f-005",
  "description": "碎月印记...",
  "planted_chapter": 27,
  "last_hinted_chapter": 81,
  "gap_since_hint": 99,
  "status": "⚠️ 遗忘风险(99章未提示)"
}

## 三向状态校验（state-files vs 正文一致性）

### 核心问题

state-files（characters.json / power_system.json / world_setting.json）是流水线的**状态持久化层**，但批量修复脚本不会自动更新它们。审查中发现 state-files 过期是最常见的 S1 问题之一。

### 校验方法

1. 提取本卷关键剧情事件（突破/死亡/获取/地点变更）
2. 对照 `characters.json` 中的 `cultivation_level` / `status` / `current_location`
3. 标记所有不一致项

### 本会话检测到的 state-files 过期案例

| 对象 | state-files 记录 | 实际剧情 | 影响 |
|------|-----------------|---------|------|
| 林尘修为 | 练气八层 (vol前) | 筑基初期 (ch48) → 金丹初期 (ch91) | 调用 generate_draft 会用旧数据 |
| 林浩然状态 | 存活 | 被林尘斩杀 (ch109) | 后续写作可能复用 |
| 林震天状态 | 存活 | 被林浩然偷袭致死 (ch103) | 同上 |

def scan_cultivation_mismatch(chapter_range):
    chars = json.load(open('state-files/characters.json'))
    for c in chars['characters']:
        name = c['name']
        expected = c.get('cultivation_level', '')
        if not expected:
            continue
        # 提取修为关键词
        level_num = re.findall(r'(练气|筑基|金丹|元婴|化神)(.*?)(?:[，。]|$)', expected)
        if not level_num:
            continue
