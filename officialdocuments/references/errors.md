# 公文写作 — 常见错误与修正

## 速查表

| # | 错误类型 | 典型症状 | 修正方向 |
|---|----------|----------|----------|
| 1 | 文种叠用 | "请示报告"连用 | 择一 |
| 2 | 文种错配 | 对不相隶属机关用请示 | 改用函 |
| 3 | 方向错误 | 下行用请示 / 上行用通知 | 按行文方向重选 |
| 4 | 一文多事 | 请示含多个独立事项 | 拆分 |
| 5 | 依据缺失 | "根据工作需要"无具体文件 | 引用文号或标"待核实" |

## 一、文种混用

### 错误1：请示报告叠用

| 项目 | 内容 |
|------|------|
| **错误** | 标题"关于申请追加预算的请示报告"，结尾"以上请示报告当否，请批复" |
| **诊断** | 请示与报告不得叠用；根据结尾"请批复"应选请示 |
| **修正** | 标题"关于申请追加预算的请示"，结尾"妥否，请批示" |

### 错误2：向不相隶属机关用请示

| 项目 | 内容 |
|------|------|
| **错误** | 向市发改委发"关于申请项目立项的请示" |
| **诊断** | 发改委与公司不相隶属，不能用请示 |
| **修正** | 改用"函"，标题"关于申请XX项目立项的函"，结尾"可否，请函复" |

### 错误3：下行文用请示

| 项目 | 内容 |
|------|------|
| **错误** | 向下级发"关于要求子公司报送材料的请示" |
| **诊断** | 向下级发文不能用请示 |
| **修正** | 改用"通知"，结尾"特此通知" |

## 九、脚本层已修复的缺陷（勿回退）

以下三处曾导致**格式正确的文档被误判、或正确文档被排错版**，均已修复。改动脚本时勿回退。

### 缺陷5：日文模板底子导致整篇变 MS 明朝（gb_gongwen.py / theme1.xml / settings.xml）

| 项目 | 内容 |
|------|------|
| **症状** | 生成/另存的 docx 在 Word 中出现「ＭＳ 明朝」字体，且**不只新增段**——原文件自带的既有段同样中招 |
| **根因** | 三处叠加：① `word/theme/theme1.xml` 是日文模板底子，`majorFont`/`minorFont` 的 `<a:ea typeface=""/>` 东亚字体槽位为空；② 字体回退表中 `Jpan`（日文）槽位正是「ＭＳ 明朝」（major 为「ＭＳ ゴシック」）；③ `word/settings.xml` 里一句 `<w:themeFontLang w:eastAsia="ja-JP"/>` 把东亚语言钉成日文 |
| **为何以前没暴露** | 旧 `gb_gongwen.py` 根本不输出 settings.xml/theme1.xml，Word 打开时用隐式主题补全；一旦经日文模板/WPS 兼容路径处理过，雷就被埋进包里 |
| **修正（新稿）** | `gb_gongwen.py` 显式输出 `word/settings.xml`（`themeFontLang eastAsia="zh-CN"`）与 `word/theme/theme1.xml`（major 的 ea=方正小标宋简体、minor 的 ea=仿宋_GB2312；Jpan 槽也钉成黑体/仿宋_GB2312），并在 `[Content_Types].xml`、`document.xml.rels` 中登记 |
| **修正（存量）** | 新增 `scripts/fix_theme_fonts.py`：只替换 a:ea 与 Jpan 槽字体、改 themeFontLang 语言，不动其他槽位、不删表；部件缺失不新增 |
| **验证** | ① 新稿解包：无 ＭＳ/明朝/ゴシック/ja-JP，a:ea 两槽非空；② 存量带雷稿修复后 qa 主题层 6 项全 PASS；③ qa_docx 新增「第三·五层」6 项自动拦截 |

```bash
# 修复存量带雷 docx（默认原地修复并留 .bak）
python scripts/fix_theme_fonts.py "稿件.docx"
# 或另存
python scripts/fix_theme_fonts.py "稿件.docx" -o "修复稿.docx"
```

> 教训：OOXML 里「没写」不等于「没有」——缺失的主题/设置部件会被 Word 用隐式默认补全，
> 而默认值可能随模板语言变化。涉及东亚字体必须**显式钉死 a:ea 槽位与 themeFontLang**，
> 不能依赖 Word 回退。该雷影响整篇（含原文件段），属包级污染，逐段改 rFonts 治标不治本。

#### 附带雷：裸 Courier 缺字弹窗（同一类包级字体污染，常并发）

| 项目 | 内容 |
|------|------|
| **症状** | 打开 docx 弹「缺失 Courier 字体，是否替换为 Courier New」 |
| **根因** | `styles.xml`/`fontTable.xml` 引用裸名 `Courier`（macro / Macro Text Char 样式 `w:ascii="Courier"`），系统只装 Courier New；fontTable 虽有 `altName=Courier New` 但 Word 仍弹窗 |
| **修正** | `fix_theme_fonts.py` 内置 `LEGACY_FONT_MAP`（Courier→Courier New），负向前瞻 `(?![\w ])` 排除 `Courier New` 本身不被误改；跑一次脚本与 MS 明朝一并消除 |
| **验证** | 全包正则复扫 `="Courier(?![\w ])"` 零命中 |

### 缺陷4：二级标题超过10项时退化为阿拉伯数字（gb_gongwen.py）

| 项目 | 内容 |
|------|------|
| **症状** | 制度类文档二级标题出现"（11）（12）"，而前文是"（九）（十）"。qa_docx.py 不报错，需人工发现 |
| **根因** | `CN_NUM = "〇一二三四五六七八九十"` 只覆盖 0-10。`_h2_num(11)` 走 `return str(n)` 兜底，输出半角 `"11"`。一级标题同类问题（>10 个一级标题时） |
| **修正** | 新增 `cn_num(n)` 支持 1-99（`二十`/`二十一`/`九十九`），`_h1_num`/`_h2_num` 统一委托它；>99 仍兜底 str(n) |
| **验证** | `cn_num(11)=='十一'`、`cn_num(25)=='二十五'`；1-10 行为不变（回归）；`ART_RE` 行首锚定不受影响 |
| **触发场景** | 制度/办法类文档，某一章内二级标题多于 10 个（如"四、采购程序"下有十二项）。**长制度必查** |

> 教训：中文序号转换必须覆盖到实际可能出现的最大值。制度类文档二级标题常见 10-20 项，
> CN_NUM 这种"只到十"的查表实现是隐患。生成后建议 grep `（\d+）` 自检二级编号是否残留阿拉伯数字
> ——注意区分：四级正文款项"（1）"是**正确**的，只有**标题行**出现才是有问题。

### 缺陷1：正文引用条款破坏编号（gb_gongwen.py）

| 项目 | 内容 |
|------|------|
| **症状** | 报告类公文中，二级编号出现"（一）（一）（二）（一）"错乱 |
| **根因** | `ART_RE` 用 `search()` 匹配正文**任意位置**的"第X条"。正文引用制度条款（如"依据《XX办法》第七条""按第十二条要求"）被误判为制度条文边界，重置了二级/三级计数器 |
| **修正** | `ART_RE` 锚定行首 `^第[X]条(?=[\s　]|$)`，调用改为 `ART_RE.match(text.lstrip())` |
| **验证** | 报告类正文含"第七条"引用时编号连续；制度类"第一条 xxx"仍正确重置 |

> 教训：制度条文边界必须**行首锚定**。引用条款是正文的正常表述，不是结构标记。

### 缺陷2：一级标题不被识别为分节边界（qa_docx.py）

| 项目 | 内容 |
|------|------|
| **症状** | 每节二级编号从"（一）"重启的**正确**公文，被报"编号不连续，期望（五）" |
| **根因** | 检查器只把"第X条"当分节边界（为制度类设计），不认"一、二、三"一级标题，于是把全文二级编号当作一条连续序列 |
| **修正** | 新增 `H1_OUT_RE`，"一、xxx"同样重置 h2/h3 计数器 |
| **副产物** | 报错信息中的"第0条区间"恒为0，修正后正确显示"第1节/第2节区间" |

### 缺陷3：表格数字被误判为编号（qa_docx.py）

| 项目 | 内容 |
|------|------|
| **症状** | 报"三级编号错误：期望 1．实际112.84万元"、"期望 113．实际363.07万元" |
| **根因** | 检查器提取全部 `<w:t>`（含表格单元格），金额"112.84万元"匹配了 `^\d+[．.]` |
| **修正** | 新增 `_extract_body_texts()`，仅遍历 `<w:body>` 直接子级的 `<w:p>`，整体跳过 `<w:tbl>`；`H3_OUT_RE` 加 `(?!\d)` 排除小数 |
| **附带收益** | 按 `<w:p>` 取整段文本后，原先靠标点猜测段落边界的 run 合并启发式逻辑被删除，更健壮 |

> 教训：编号连续性只针对正文段落。表格里的金额、比率、行号不是编号。

### 排查方法

编号异常时，先用解析层定位，不要盲改 md：

```bash
python -c "
import sys; sys.path.insert(0,'<skill>/scripts')
from gb_gongwen import markdown_to_parts, ART_RE
for p in markdown_to_parts(open('稿件.md',encoding='utf-8').read()):
    if p[0] in ('14','15','16'): print(p[0],'|',p[1][:40])
    elif p[0]=='19' and ART_RE.match(str(p[1]).lstrip()): print('!!RESET:',str(p[1])[:50])
"
```

看到非预期的 `!!RESET` 即为边界误判。**质检报错时先判断是文档问题还是检查器误报**——用负向样例（故意跳号）确认检查器仍有效，再决定改文档还是改脚本。

### 缺陷6 / 陷阱：损坏与异常 docx 的甄别与恢复（批量修复必读）

批量扫描大目录时（实测 ~680 个 docx），约 2% 是非 zip 的「假 docx」，扫描脚本必须捕获 `zipfile.BadZipFile` 异常跳过，否则整批中断。甄别靠**读文件头 8 字节**：

| 文件头 | 类型 | 处理 |
|--------|------|------|
| `00 00...`（0 字节或全零） | 空壳/同步中断 | 确认无正常副本后删除（删除前重新实测，可能期间已被填充） |
| `00 05 16 07` | macOS 资源叉垃圾（`__MACOSX\._xxx`） | 直接删除，真身在同级目录 |
| `F1 03 F2 03 F3 03 F4 03` | WPS 加密/私有封装 | WPS COM `KWPS.Application` → `Documents.Open(path,$false,$true)` → `SaveAs2(out, 12)` 转标准 docx；转换稿沿用日文主题，**转换后必须再跑 fix_theme_fonts.py** |
| `50 4B 03 04` 但报 "End of Central Directory record could not be found" | 半截 zip（写到一半被截断） | 本地文件头仍完整：扫 `PK\x03\x04` 逐条按 csize/method 解压重打包即可抢救全部内容（实测完整恢复 11 个部件含 48KB document.xml） |
| 打开报 "used by another process" | 文件被 Word/WPS 占用 | 非损坏；让用户关闭后重试 |

注意事项：

- WPS COM 用 `KWPS.Application`（非 `WPS.Application`）；`Visible=false`、`DisplayAlerts=0` 防弹窗；
- 恢复/转换产物命名 `_抢救_`/`_转换_` 前缀，验证内容完整并修复字体后**替换回原文件名**；
- 批量修复流程：扫描 → 逐个 `.bak` 备份（已存在不覆盖）→ 修复 → **复扫验证通过才算成功** → 临时脚本用完即删。

### 修复稿必须验证「内容零影响」

对存量 docx 做任何包级修复（`fix_theme_fonts.py` 等）前，先产出 `-o` 测试稿，用 [`diff_docx_parts.md`](diff_docx_parts.md) 的比对脚本验证：

- 部件清单前后无增减；
- 非目标部件（除 `theme1.xml`/`settings.xml` 及命令行允许项外）字节完全一致；
- `word/document.xml` 逐段 `<w:t>` 文本 diff 为空（实测 552 段零差异）。

结果报告给用户、经目检确认后才原地修复原件。文件被 Word/WPS 占用时 zip 打开会报 "used by another process"，需先关闭。

### 缺陷7 / 陷阱：WPS 宏产物主题丢失（日文底子）——改模板治不了，只能换新建载体

**现象**：`word.bas` 公文宏（`自动格式化文档`）产出的 docx，`theme1.xml` 里 `majorFont/minorFont` 的 `a:ea` 为空、`Jpan=游明朝/游ゴシック Light`、`latin=Calibri`，触发第三·五层主题拦截。而 Normal.dotm **本体**的 theme1.xml 是干净的（方正小标宋简体/仿宋_GB2312/黑体/Times New Roman）。

**六组实验证伪（2026-11-05，WPS 12.1.0.29158）**：

| 尝试 | 结果 |
|---|---|
| 改写 `WPS.thmx`（应用默认主题）| 新文档仍日文底子 → 无效，已回滚 |
| `Documents.Add()` 无参 | 日文底子 |
| `Documents.Add(Normal.dotm)` 显式指定 | 仍日文底子（**不继承**） |
| `Documents.Add(同内容改名的 .dotm 副本)` | **主题干净** → 文件内容本身没问题 |
| `ApplyTheme(...)` | 返回成功但零效果 |
| `DocumentTheme.ThemeFonts` | 对象模型缺失（WPS 未实现） |

**根因**：`游明朝/游ゴシック` 以 UTF-16 硬编码在 `office6/wpscore.dll`（全盘主题资源中无此字符串）；WPS 对**名为 Normal.dotm 的默认模板**做特例——样式/宏照常加载，`theme1.xml` 被强制替换为内置日文主题。

**因此**：改 Normal.dotm 的 theme 部件、改 WPS.thmx、宏内写主题，三条路全部不通。对「打开既有文档跑宏」更天然无效——主题来自原文档本身。

**判定「是否有实际影响」**：宏产物 `w:*Theme` 引用数为 **0**（字体全显式 + `docDefaults` 钉 `eastAsia=仿宋_GB2312`），空 `a:ea` 槽与 Jpan 回退**永不被触发**，渲染 100% 正确。`qa_docx.py` 自 2.4.1 起用 `_theme_inert()` 识别此情形并降为 WARNING；`refs>0` 或 docDefaults 无东亚字体的真带雷文档仍阻断。

**根治做法**：用 **`中言公文模板.dotx`**（`%APPDATA%\kingsoft\office6\templates\`）新建文档再跑宏。该模板由 Normal.dotm 派生：保留 styles/settings/theme/sectPr，剥离 `vbaProject.bin`/`vbaData.xml`，`[Content_Types].xml` 主文档类型改为 `...template.main+xml`。实测新建 → 跑「自动格式化文档」→ 落盘，主题 ea=方正小标宋简体/仿宋_GB2312、Jpan=黑体/仿宋，**31/31 全绿、0 告警**。

**兜底**：对已在既有文档上跑过宏的成品，`python scripts/fix_theme_fonts.py "稿件.docx"` 原地修复（目标值与 Normal.dotm 本体一致）。

### 缺陷8 / 陷阱：多节文档跑宏后「整篇变横向」（清理空行删掉了分节符）

**现象**：正文纵向 + 附件宽表横向的多节文档，跑 `自动格式化文档` 后节数 2→1，整篇变成末节的横向版式。

**根因**：分节符保存在**段落属性** `pPr/sectPr` 中，该段正文通常只有一个段落标记（`Range.Text` 长度=1，实测为 `\x0c`）。`清理空行` 的判据是 `Len(text) = 1`，把它当空行删掉 → 分节符消失 → 末节页面设置（横向）接管全文。

**修法**（word.bas v2.2）：删空行前先登记各节末段 `ActiveDocument.Sections(i).Range.Paragraphs.Last.Range.Start` 到 Dictionary，删到这些位置时跳过。从后向前删除不会使已登记的起始位置失效。

**排查要点**：
- 用 `doc.Sections.Count` 在宏执行前后比对，最直接；
- 仅看 `document.xml` 的 `sectPr` 数即可确认（2→1 即中招）；
- 手工复现时 `Application.Run("自动格式化文档")` 会**优先命中 Normal.dotm 的全局宏**，注入到测试文档里的同名副本不会被执行——测试须给入口改名（如 `自动格式化文档_v22`）。

**顺带**：`Range.Text` 里 `\x07` 是单元格结束标记，`\r\x07` 长度为 2，不会被误删，无需特殊处理。

### 缺陷9：加统一页面设置时踩到的三个坑（word.bas v2.3）

1. **`PaperSize` 会重置 `Orientation`**。必须先读 `isLand = (ps.Orientation = wdOrientLandscape)`，再设 `ps.PaperSize = wdPaperA4`，**最后**才把 `Orientation` 套回去。顺序颠倒会把横向节压成纵向。
2. **横向节的边距要换轴**。纵向按 GB/T 9704 用 `上37/下35/左28/右26mm`；A4 横置后装订线仍在长边方向，应改为 `上26/下26/左35/右37mm`（左右取原来的下/上边距），否则文字区偏窄、纵向不居中。
3. **落款不一定在文末**。以「附件：xxx」+ 附表收尾的公文，落款在这句说明**之前**。`格式化落款` 需先倒序找最后一个 `附件：`/`附件:` 开头的段落作为扫描上界，找不到才回退到文末。

**落款右缘对齐的实现**：不用左缩进，用**右缩进**。较长者（署名）右空四字 = `SIGN_RIGHT_INDENT`（64pt），较短者（日期）额外多空两字 = 112pt，两者右缘落在同一竖直线，符合 GB/T 9704。

### 陷阱：GB/T 9704 厘米值转 twips 有取整误差，比较需容差

`3.5cm = 1984.25 twips`，WPS/Word 落盘为 `1984`，与 `PAGE_SPEC` 的 `1985` 差 1 就被判「不合规」——这是假差异。`qa_docx.py` 的页边距比较已改为 **±2 twips 容差**：取整差放行，真实偏差（实测负样本改成 1440）仍阻断。

### 陷阱：`doc.Save()` 前的核验代码抛异常，会让格式改动全部丢失

脚本写成「跑宏 → 核验 → 保存」时，核验段一旦抛 COM 异常（如对无第 2 行的表格调 `Tables(1).Cell(2,1)`），`Save` 就被跳过，文件仍是原件。**必须把保存紧跟在宏之后**，核验另起只读脚本。
