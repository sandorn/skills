# 公文排版规范（GB/T 9704-2012）

本规范用于 `officialdocuments` skill 生成正式 `.docx` 报告、请示、通知、函件等文档。生成 Word 正式稿时，优先调用 `scripts/gb_gongwen.py`，不得只用 Markdown 或 pandoc 裸转。

## 页面设置

| 项目 | 参数 |
| :--- | :--- |
| 纸张 | A4（210mm × 297mm；WordprocessingML：11906 × 16838 twips） |
| 页边距 | 上 37mm / 下 35mm / 左 28mm / 右 26mm |
| 行距 | 固定值 30 磅（600 twips） |
| 文档网格 | 每页 22 行、每行 28 字（脚本写入 `docGrid`；最终以 Word 渲染为准） |

## 字体样式

| 元素 | 字体 | 字号 | 样式号 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 主标题 | 方正小标宋简体 | 二号（22pt） | 13 | 居中，段后空一行（二号字高） |
| 一级标题 | 黑体 | 三号（16pt） | 14 | 首行缩进 2 字符；编号 `一、` |
| 二级标题 | 楷体_GB2312 | 三号（16pt） | 15 | 首行缩进 2 字符；编号 `（一）` |
| 三级标题 | 仿宋_GB2312 | 三号（16pt） | 16 | 首行缩进 2 字符；加粗；编号 `1．` |
| 四级及以下 | 仿宋_GB2312 | 三号（16pt） | — | 首行缩进 2 字符；编号 `（1）`，必要时人工处理 |
| 正文 | 仿宋_GB2312 | 三号（16pt） | 19 | 首行缩进 2 字符，两端对齐 |
| 附件说明 | 仿宋_GB2312 | 三号（16pt） | — | 正文下空一行，左空二字 |
| 附件标识 | 黑体 | 三号（16pt） | — | 顶格，版心左上角第一行 |
| 页码 | 宋体（半角） | 四号（14pt） | — | 一字线，距版心下边缘 2mm；脚本暂不自动加页码 |

## 标题序号

标题序号由 `gb_gongwen.py` 统一生成：

- 一级标题：`一、二、三……`
- 二级标题：`（一）（二）（三）……`
- 三级标题：`1．2．3．……`

同级标题自动递增，遇到上级标题时下级计数器归零。调用 `generate(parts, output)` 时，标题文本中不要写编号；命令行从 Markdown 读取时，如原文已带编号，脚本会识别并去掉编号后重新统一编号。

## 落款

发文机关署名与成文日期作为整体处理：

- 正文后空两行。
- 较长者右空四字，较短者与较长者居中对齐。
- 脚本优先用 Pillow + `C:/Windows/Fonts/simfang.ttf` 实测文字宽度计算 `left_indent`；无 Pillow 时按中文全角宽度估算兜底。
- 如正式印发前对落款视觉位置要求很高，应在 Word 标尺上复核并微调。

## 脚本接口

### Python 接口

```python
from gb_gongwen import generate

parts = [
    ("13", "关于XXX的报告"),
    ("19", "正文内容……", True),
    ("14", "主要问题"),      # 自动生成“一、主要问题”
    ("15", "具体表现"),      # 自动生成“（一）具体表现”
    ("16", "制度建设方面"),  # 自动生成“1．制度建设方面”
    ("19", "正文……", True),
    ("sign", "发文机关", "2026年6月19日"),
]

generate(parts, "output.docx")
```

### 命令行接口

```bash
python ~/.agents/skills/officialdocuments/scripts/gb_gongwen.py \
  "输入.md" "输出.docx" \
  --author "子公司管理室" \
  --date "2026年6月19日"
```

## 模板策略

如用户要求沿用特定 Word 模板（含复杂页眉页脚、图片、表格），可使用 pandoc `--reference-doc` 方案。默认正式公文交付优先使用 `gb_gongwen.py`——不依赖 Word、pandoc 样式映射或 python-docx，稳定写入核心公文版式。

## 生成后验证（交付质量门）

每次生成 `.docx` 后必须验证以下 8 项，缺一不可。用户要求"可报送专业版式"时，**8 项全部通过才算合格**，任一项不通过必须返工。

### 8 项必验清单

| # | 验证项 | 标准 | 验证方法 |
|---|--------|------|----------|
| 1 | 页面尺寸 | 上 3.7cm、下 3.5cm、左 2.8cm、右 2.6cm | 解压 docx，查 `word/document.xml` 中 `<w:pgMar>` 的 `w:top="2098" w:bottom="1985" w:left="1588" w:right="1474"` |
| 2 | 标题字体 | 方正小标宋简体，二号（22pt），居中 | 查 `word/styles.xml` 中 styleId="13" 的 `<w:rFonts w:eastAsia="方正小标宋简体"/>` 和 `<w:sz w:val="44"/>` |
| 3 | 正文字体 | 仿宋_GB2312，三号（16pt） | 查 `word/styles.xml` 中 styleId="19" 的 `<w:rFonts w:eastAsia="仿宋_GB2312"/>` 和 `<w:sz w:val="32"/>` |
| 4 | 一级标题 | 黑体，三号，编号"一、" | 查 styleId="14"：`<w:rFonts w:eastAsia="黑体"/>`；正文中含"一、…" |
| 5 | 二级标题 | 楷体_GB2312，三号，编号"（一）" | 查 styleId="15"：`<w:rFonts w:eastAsia="楷体_GB2312"/>`；正文中含"（一）…" |
| 6 | 段落版式 | 首行缩进 2 字符，固定 30 磅行距 | 查 `<w:ind w:firstLine="640"/>` 和 `<w:spacing w:line="600" w:lineRule="exact"/>` |
| 7 | 内容完整性 | 标题、各级标题、正文关键段落均完整写入，落款署名与日期存在 | 不能只验证文件存在，须在 `word/document.xml` 中 grep 关键文本片段 |
| 8 | 产物报告 | 输出路径、文件大小、XML 样式检查结果在最终回复中说明 | 回复格式参见下方"验证报告模板" |

### 验证方法

解压 `.docx`（本质是 ZIP），检查 `word/document.xml` 与 `word/styles.xml` 中的字体、字号、页边距、缩进、行距：

```bash
# 解压并检查关键样式
unzip -p 输出.docx word/styles.xml | grep -o 'eastAsia="[^"]*"'
unzip -p 输出.docx word/document.xml | grep -o 'w:firstLine="[^"]*"'
unzip -p 输出.docx word/document.xml | grep -o 'w:top="[^"]*"'
```

正式报送前须人工打开 Word 检查分页、图片、落款和页码。脚本暂不自动添加页码。

### 验证不通过时的处理

| 问题 | 修复方向 |
|------|----------|
| 页边距/字体/行距不对 | 检查脚本 `STYLES` 与 `PAGE` 常量是否被意外修改 |
| 标题重复编号 | 输入 Markdown 带编号 → 脚本自动去重编号，检查是否生效 |
| 落款位置偏移 | 安装 Pillow 可获得精确落款宽度；否则用中文全角估算兜底 |
| 内容缺失 | 检查 Markdown 是否包含图片语法（`![...]` 会被跳过）；检查输入编码（须 UTF-8） |
| 脚本不可用 | 优先修复脚本；不要退回到无样式保障的 pandoc 默认导出 |

### 失败信号（表明未做版式验证）

- 只说"已生成 docx"，但没有验证版式
- 生成的文档能打开但像普通笔记/Markdown 导出
- skill 参考资料里有格式要求，但没有按此节逐项验证

### 推荐流程

1. 将正文整理为结构化 Markdown（标题行、`一、...`、`（一）...`）
2. 使用 `scripts/gb_gongwen.py` 生成 `.docx`
3. 按上述 8 项逐项验证，回复中附验证报告
4. 如脚本缺失或失效，优先修复脚本；不要退回到无样式保障的 pandoc 默认导出
