# 公文/制度起草前置检查（Preflight）

## 角色

本 skill 是 `officialdocuments` 的**前置守门层**。它不负责排版与文风——那是 `officialdocuments` 的职责。
它负责两件事：**场景 A（起草前）**——确保动手之前已知既有文件库中有什么、母本要求什么、用户实际管理模式；**场景 B（审查时）**——对已完稿制度做系统性审查，找出口径矛盾、权限倒挂、附件空壳等实质问题。

> **铁律：不得在未完成"零、一"两节的情况下开始撰写正文。**
> 违反此律的典型后果：全稿完成后才发现同主题已有【待审定】在推稿或已发布版本，整稿定位错误，需推倒重来。

---

## 触发条件

- "参照【某制度】撰写【本单位某制度】"
- "起草/制定/修订 XX 管理办法、实施细则、管理规定、制度"
- "集团/母公司有制度，子公司在下面，请写一份对标的"
- 任何会产出 docx 且篇幅超过 1 页的制度类文档
- **用户说"审查/把关/评审/提意见"一份已写好的制度稿**（场景 B：完成稿审查）

## 场景 A：起草前前置检查（原 skill 职责）

## 零、既有文件库审计（强制，先做）

**目标：在写一个字之前，查清目标目录中是否已有同主题文件。**

### 检索清单（逐项执行）

| # | 检索对象 | 方法 |
|---|----------|------|
| 1 | 文件名同主题 | `search_files(target='files', pattern='*关键词*')` |
| 2 | 正文同主题 | `search_files(target='content', pattern='关键词1\\|关键词2')` |
| 3 | **历年版本** | 匹配 `（2024版）` `（2025版）` `V1.0` `（2024.10版）` 等年份/版本后缀 |
| 4 | **中间态稿件** | 匹配 `【清洁版】` `【送审稿】` `-待审定` `[草案]` `_v0` `(2)` 等 |
| 5 | **正式发布件** | 优先找 `.pdf`——往往带红头文号与印发日期，是**现行有效版本** |
| 6 | **母本** | `集团参考制度/`、`母公司制度/` 等目录下的对应制度 |

### 决策矩阵

| 审计结果 | 处理方式 |
|----------|----------|
| 无同主题文件 | 进入第一节，正常起草 |
| 有**已发布**版本（带文号/印发日期） | 先问用户：本次是**修订**（改文号、留原结构）还是**废止重制**（附则写明废止条款） |
| 有**待审定/清洁版**在推稿 | **立即暂停起草**，向用户报告并列出差异表，由用户决策：<br>（A）以新稿替换 （B）以在推稿为基线修订 （C）仅供对比 |
| 有**集团母本** | 正常参照，在"目的与依据"条中明确引用 |

### 硬性要求

1. **发现并存稿件时，先报告再动手。** 不擅自选择替换或合并，不静默产出平行稿。
2. **差异表维度固定**（逐条列出，不笼统描述）：
   治理架构 / 执行机构 / 部门表述 / 限额分档 / 审批链条 / 附件清单 / 解释权部门 / 引用母本方式 / 篇幅条数
3. **报告后等待用户选择路径**，不替用户决策。

### 陷阱

- **`.doc`（旧格式）需先转换才能检索内容**——Word COM 转 txt 后再读（见 `references/word-com-extraction.md`）。
- **文件大小异常大的 docx**（如 600KB+）通常内嵌 logo/图片，说明是**成稿而非草稿**，很可能是在推版本。
- 公司制度目录下常有 `【清洁版】` 前缀的稿件——这是**已定稿待审定**的强信号，不是草稿。

## 一、起草前澄清（制度类专项）

**目标：把用户的管理模式问清楚，而不是照搬母本架构。**

### 呈现方式（三段式）

1. **母本要点表** —— 先列出上级/集团制度的关键设计（治理架构、限额、流程）
2. **本单位建议方案** —— 给出你的建议值，并说明倾向理由
3. **待确认事项编号清单** —— 让用户按序号逐条回复

用户看到对比后再决策，返工率显著降低。

### 必问清单

| 确认项 | 说明 |
|--------|------|
| 主体与适用范围 | 以哪个法人名义发？本部/分公司/子公司如何适用？ |
| 决策机构 | 新设专门机构（委员会/领导小组），还是**复用既有机构**（总经理办公会等）？**优先复用——不新增机构即不增加落地动作** |
| 部门表述 | 用真实部门名，还是弹性代称（"承担XX职能的部门"）？ |
| 业务边界 | 覆盖范围清单；与既有专项制度（如食堂采购）如何衔接——通常留接口"另有规定的从其规定" |
| 限额与门槛 | 逐档给建议值；**必须问清业务规模量级**，否则门槛设置可能完全不适用 |
| 审批分档 | 是否分档；报母公司审批的部分遵从母公司要求 |
| 程序颗粒度 | 完整保留 / 原则性表述 / 框架+细节下沉（**推荐后者**，符合"正确的废话"风格，减少执行动作） |
| 附件清单 | 逐个确认保留哪些，**不默认照搬母本全部附件** |
| 篇幅目标 | 条数或页数 |
| 名称与版本 | 全称 + 年份版本 |
| "留活口"事项 | 用户可能要求某些决策"在执行时再定"而非写死。设计为：制度写"按公司授权体系及相关议事规则流转审批"+ 弹性条款，不写死必须上会 |

## 场景 B：审查时

**目标：对用户已完稿的制度做系统性审查，找出口径矛盾、权限倒挂、附件空壳等实质问题。**

### 审查五步法

1. **版本谱系追溯**：与旧版/在推稿/上位制度逐条对比，识别弱化或越权点
2. **结构与附件检查**：附件是否空壳、附则是否有追溯适用条款
3. **实体内容审查——聚焦四个维度的新发现**：
   - **价格体系双轨道**：区分"体系价调整"与"成交价折扣"两个层级的权限，检查标准折扣叠加后上限是否倒挂体系价底线。标准折扣已达15%而体系调整上限10%——典型的权限倒挂，须统一计算基数并加兜底（"折扣后有效租金不低于体系规定下限"）
   - **审批表述质量**："XX的审批"句式（如"扩租部分按XX执行的审批"）是事项描述还是审批授权？应改为"由XX审批"或"按XX办理"——消除赘余的审批授意，与附件清单口径保持一致
   - **合同衔接**：制度中的天数/比例/倍数与现行合同是否一致。不一致时：如果是管理依据须写"按合同约定"衔接语
   - **弹性措辞**：频次用弹性词而不写死（符合用户"正确的废话"偏好）；"原则上"全部有例外路径
4. **陷阱扫描**：部门称谓、术语定义、保密外部约束、自动升级触发条件
5. **输出**：实质性必改项 → 建议修改项 → 上会前确认项 → 是否出清洁版

## 二、移交 drafting

澄清完毕后，**将正文撰写与排版交由 `officialdocuments` skill 执行**。
本 skill 的产出是：

- 既有文件审计报告（如有并存稿件）
- 母本要点 vs 本单位建议 对比表
- 用户已确认的参数清单
